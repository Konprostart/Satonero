# Independent Satonero operation

This document lists what an operator has to provide to run Satonero without
Mostro-controlled infrastructure, what is already optional, and what the
regtest gates have actually demonstrated. It is a checklist, not a claim of
production readiness.

## What the daemon requires

The daemon reads everything it needs from `settings.toml` and its LND
credentials; it does not contact a Mostro service in order to operate. One
Mostro-owned value is compiled into the binary — the inherited development-fee
Lightning address (see the Dev fee row) — and it stays inert unless an operator
both enables the development fee and runs on mainnet.

| Requirement | Where it comes from | Notes |
|---|---|---|
| Nostr relay(s) | `nostr.relays` in `settings.toml` | Any NIP-01 relay; the daemon publishes its kind-10002 list from these values. |
| Node keys | `nostr.nsec_privkey` | Generated by `mostrod --generate-keys` or the setup wizard. |
| LND connection | `lightning.lnd_cert_file`, `lightning.lnd_macaroon_file`, `lightning.lnd_grpc_host` | The node must be able to open channels, create hold invoices and pay. |
| Operator fee | `mostro.fee` | Set to `0` for a fee-free instance. |
| Dev fee | `mostro.dev_fee_enabled`, `mostro.dev_fee_lightning_address` | Template default is `false`. When enabled without `dev_fee_lightning_address`, the compiled fallback is `dev@pay.mostro.foundation` (`src/config/constants.rs`); the payment path is mainnet-only. |
| Anti-abuse bond | `anti_abuse_bond` section | Opt-in; absent or disabled means no bond. |
| Cashu escrow | `cashu` section | Opt-in; absent or disabled means Lightning-only escrow. |

### How clients discover the operator's relays

Relay URLs are not carried by the kind-38385 info event. A scheduler job,
`job_relay_list` in `src/scheduler.rs`, builds a NIP-65 kind-10002 relay list
signed with the daemon key: one `r` tag per connected relay from
`nostr.relays`, published at startup and repeated every
`mostro.publish_relays_interval` seconds (template default: 60).

The mobile app subscribes to a filter of `{kinds: [10002], authors: [<daemon
pubkey>], limit: 1}` and adds the advertised relays to its relay list; bootstrap
relays that the list does not mention stay connected but idle. That is how a
client reaches the operator's relay without being told its URL in advance.

## What the mobile app still defaults to

The client is usable against an arbitrary daemon, but three defaults, plus the
bundled community list, point at Mostro community infrastructure. An
independent deployment must avoid or replace them.

- **Bootstrap relays.** `wss://nos.lol` and `wss://relay.damus.io`
  (`lib/core/config.dart`) are discovery relays used to fetch the configured
  node's kind-10002 list. They are not seeded into the visible relay list and
  are not required when the operator's relay is reachable; a test build can
  replace them with the seeded local relay list instead.
- **Default community node.** The "Skip" choice (`_onSkip` in
  `community_selector_screen.dart`) asks for confirmation and then selects the
  Mostro community node `82fa8cb9...8390`, which is also the "Default" entry of
  the bundled `trustedCommunities` list (`lib/core/config/communities.dart`).
  For an independent instance, choose **Use a custom node**, or pre-seed
  `mostro_settings` with the operator's daemon pubkey and relay.
- **Trusted communities.** `trustedCommunities` lists third-party Mostro
  communities mirrored from mostro.community, and the selector renders them as
  ready-made choices. An independent deployment should treat them as
  third-party nodes, not as Satonero services.
- **Push notifications.** `pushServerUrl` is a compile-time define
  (`lib/core/config.dart`, `PUSH_SERVER_URL`). When it is empty, push
  registration is skipped and no external service is contacted.

## What the regtest gates demonstrated

The Phase 6A, 6B and 6C runs drive the real Android app against a real daemon
on a disposable stack (bitcoind, three LND nodes, one self-hosted relay). No
Mostro relay, community node, push server or dev-fee infrastructure is used.

- Phase 6A (`43223500816`): the app discovers the maker's order through a
  self-hosted relay, takes it, submits a payout invoice and reaches `active`.
- Phase 6B (`43255923049`): the app sends `fiat-sent`, the seller releases, the
  daemon settles the hold invoice, pays the buyer and the order reaches
  `success`.
- Phase 6C (`43283643290`): the app rates the seller, the daemon publishes a
  signed kind-38384 aggregate, and the app renders the updated reputation.
  Invalid, unknown-order, non-participant and duplicate ratings create no
  event.

## Known gaps

- The mobile "Skip" default still selects the community node. A build can pin a
  different daemon with `--dart-define=MOSTRO_PUB_KEY=<hex>` (empty by default;
  the legacy upstream pubkey is rejected and resolves to "no daemon
  configured"), but that pin only sets the initially configured daemon — it
  does not change which node the Skip button selects after confirmation.
- Public relays and physical devices have not been exercised; every gate runs
  on a disposable regtest relay and an x86_64 emulator.
- The relay read helper used by the gates prefers a host-side client because
  in-container reads against the test relay returned no events in some runs;
  the cause of that divergence is still unknown.
- Settlement is irreversible by design: evaluate `queryroutes` and channel
  liquidity before releasing a hold invoice.
